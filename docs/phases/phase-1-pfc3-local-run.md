# PFC #3 local synthetic run

This separately approved bounded slice uses PostgreSQL and two sequentially orchestrated logical workers. Set `FAILUREMESH_DATABASE_URL` to the same safe local synthetic database used by the earlier slices. Run `go run ./cmd/failuremesh pfc3 init`, then `go run ./cmd/failuremesh pfc3 match vulnerable`, `go run ./cmd/failuremesh pfc3 plan vulnerable`, `go run ./cmd/failuremesh pfc3 reset`, and `go run ./cmd/failuremesh pfc3 run vulnerable`. Reset again before `go run ./cmd/failuremesh pfc3 run remediated`; `match` and `plan` also accept `remediated`.

The logical sequence is A acquiring token 1 at tick 0, A starting and stalling, expiry at tick 1, B acquiring durable token 2, B committing, then A resuming with token 1 and attempting a protected write. The vulnerable write ignores the token. The remediated write locks the resource row and checks its current token in the same PostgreSQL transaction as the attempt and effect insert. The durable history, trace, attempts, resource state, and effects are re-read by the sole exported positive-verdict verifier. The fault is a bounded worker delay/stall, modeled as a deterministic pause/resume operation as the bounded delay class of V0 faults, not a new company-wide primitive. Execution uses no sleeps, scheduling race, or external lease provider.

The result proves only this PFC/version, build, synthetic environment, single resource, two logical workers, one deterministic expiry/reacquisition interleaving, and recorded invariant. Sequential orchestration models overlapping logical work; it does not test actual concurrent workers. It does not establish real distributed lease-service semantics, clock drift, scheduler behavior, network partitions, etcd/ZooKeeper/Redis/Kubernetes portability, customer applicability, production resilience, or universal stale-worker protection. The PFC remains L0 CANDIDATE; Gate A remains REVISE at 8/10 qualifying public observed incidents with families 1 and 3 unresolved.
