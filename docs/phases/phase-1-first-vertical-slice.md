# Phase 1: timeout-after-external-commit vertical slice

Status: future implementation specification, not implemented. Entry requires Phase 0 acceptance and completion of Validation Gate A (10 public incidents encoded only as L0 candidate PFCs, abstraction-fit review, and 3 specified reference architecture shapes). Gate A does not reproduce or verify PFCs. Phase 1 remains the first implementation vertical slice. The sole objective is to demonstrate the baseline flow against a Go application, PostgreSQL, and an external payment simulator. Phase 1 does not implement the other nine PFC families, a SaaS dashboard, billing, RBAC, uncontrolled production chaos, global ingestion, a large connector ecosystem, or Phase 2+ features.

## System and contract obligations

Build one Docker-runnable reference flow in which a Go service accepts a logical payment operation, records business state in PostgreSQL, calls the external payment simulator, and retries on a lost/timeout response. The simulator maintains an authoritative append-only effect ledger keyed by physical effect ID and correlated to logical operation ID. The vulnerable configuration deliberately lacks an effective idempotency/reconciliation control. The remediated configuration must use idempotency and/or reconciliation to prevent duplicate logical effects. Document simulator semantics and transaction boundaries; do not assume a database transaction atomically covers the external side effect.

Instantiate a versioned timeout-after-external-commit PFC with prerequisites, missing control, causal sequence, forbidden duplicate effect, invariant **at most one committed provider effect per logical payment operation**, abstract response-loss-after-commit experiment, required observations, and level-1 safety ceiling. Instantiate a versioned AC for the reference flow with evidenced Go/build identity, PostgreSQL boundary, payment request/effect boundary, timeout/retry policy, idempotency/reconciliation state, provider guarantee, logical-operation identity, and effect-ledger observability. Define a deterministic proof format that records the fields in [proof.md](../architecture/proof.md). Implement only the minimal CLI and adapters needed for this slice; keep v0-wide targets as later work.

## Applicability obligations

On the vulnerable AC, the matcher must return `APPLICABLE` with each prerequisite and supporting fact. On a fixture with a decisively absent necessary prerequisite, return `NOT_APPLICABLE` with evidence. On missing, stale, or conflicting retry/provider facts, return `UNKNOWN` and prohibit injection. Reevaluate after remediation: idempotency/reconciliation is a control-under-test, not a generic necessary applicability prerequisite. If the causal experiment remains meaningful and executable, the remediated AC stays `APPLICABLE` and compilation of the same experiment remains allowed. Only an explicit, evidenced PFC exclusion that makes the experiment itself impossible or meaningless permits `NOT_APPLICABLE`; execution is needed for scoped resilience.

## Experiment and safety obligations

Compile a manifest pinning PFC/AC versions, build, environment, fault location, retry count/timing, concurrency, invariant, observers, reset procedure, and verifier/adapter versions. In a synthetic level-1 environment, use a test-only deterministic simulator barrier keyed by run and logical-operation identity. It must durably append/commit the provider effect, establish authoritative commit evidence, hold the success response before caller delivery, then trigger configured response loss so the caller observes timeout/loss and follows its normal retry path. Record the barrier transitions, commit, response-loss, and retry evidence. Arbitrary sleeps or wall-clock races cannot establish fault placement. Allow the Go caller's normal retry; record the retry and every resulting provider effect. A pre-commit dropped request is an invalid test for this PFC. Bound duration and request count, reset PostgreSQL and simulator ledger between independent runs, and abort on unmet preconditions. No production adapter or level-5 execution belongs in Phase 1.

## Verdict and acceptance obligations

The vulnerable run must demonstrate one logical operation, first committed effect, response loss, retry, second distinct committed effect, and violation of the at-most-one invariant. The verifier emits `EXPOSED` with a deterministic counterexample: pinned versions/build/configuration, initial state, run/operation IDs, ordered fault and requests, both effect IDs, invariant evaluation, local evidence references/digests, replay and reset instructions. A timeout or retry without two committed effects must not be called exposure.

After remediation, rerun the same declared finite experiment space on a pinned new build. Show that the fault occurs and retry path executes while the complete effect ledger contains exactly one committed logical effect for each operation. The verifier emits `PROVEN_RESILIENT` only if every in-scope run satisfies the invariant, all required observers are complete, and the safety plan remained valid. The bundle explicitly binds PFC version, new build identity, environment, invariant, experiment space, and collected evidence. It does not assert immunity beyond that scope. Any failed injection placement, missing ledger completeness, flaky reset, aborted run, or incomplete experiment set yields `UNKNOWN` with a reason.

Automated checks must reject pre-commit response loss as this PFC, prove the post-commit/pre-success barrier is reached deterministically, show identical controlled inputs produce the same causal placement, and prove reset/isolation prevents prior runs contaminating evidence. Timing measurements may be evidence but cannot establish placement. Automated checks must exercise both verdict paths and the unknown paths, compare evidence to the authoritative ledger, verify replay from clean state, and ensure deterministic verdicts from identical evidence. Repeat runs to establish stable reproduction for an eventual L2 claim; do not promote to L3 or L4 based on this one reference architecture. The implementation agent must run repository checks and update HANDOFF.md with what was actually built and tested.
